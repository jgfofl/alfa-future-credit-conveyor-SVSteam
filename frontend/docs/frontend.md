# Веб-интерфейс: личные кабинеты клиента и сотрудника банка

Статический SPA без сборки (HTML + CSS + чистый JavaScript, без внешних библиотек и CDN), раздаётся nginx. Адаптивный (десктоп и телефон), только веб — как требует кейс.

## Запуск
- Вместе со всем: `docker compose up --build` → кабинеты на http://localhost:8080, Swagger ML-сервиса на http://localhost:8000/docs.
- Локально без Docker: `uvicorn app.main:app --port 8000` и `python -m http.server 8080 -d frontend`, затем открыть `http://localhost:8080/?ml=http://localhost:8000`.
- Сброс данных: ссылка «Сбросить демо-данные» в подвале.

## Демо-доступ (пароль `demo`)
| Роль | Логин | Что показывает |
|---|---|---|
| Предприниматель | `client@demo` | ООО «Ромашка Трейд», уже есть выданный кредит; данные компании и финансы подставляются в новую заявку |
| Предприниматель | `ip@demo` | чистый кабинет без заявок |
| Сотрудник банка | `bank@demo`, `risk@demo` | очередь с семью заявками во всех статусах |
Есть и регистрация нового клиента.

Тестовые ИНН на шаге «Компания»: `7701234567` — действует (автоодобрение); `7701234500` — ликвидирована (блокировка); `770123456799` — бюро кредитных историй недоступно (передача сотруднику); `abc…` / неверная длина — ошибка. Файл с финансовыми показателями для автозаполнения скачивается по ссылке «Скачать образец» на шаге «Финансы».

## Как интерфейс отвечает требованиям кейса
| Требование кейса | Реализация |
|---|---|
| Клиент выбирает продукт | Шаг 1: выбор по цели («закрыть кассовый разрыв» → овердрафт, с пометкой «Рекомендуем») или напрямую из 4 продуктов |
| Заполняет заявку | Мастер из 6 шагов: продукт, сумма/срок с калькулятором платежа, компания (поиск по ИНН в реестре), финансы, документы, проверка и согласие |
| Загружает данные | Документы по слотам; автозаполнение финансов из JSON/CSV |
| Видит статус | Полоса этапов «Заявка → Проверка → Решение → Подписание → Выдача», карточка статуса с понятным следующим действием, история событий, уведомления в кабинете |
| Кабинет сотрудника, обработка данных | Очередь с KPI, фильтрами и поиском; карточка заявки: данные клиента, финансы, проверки (ЕГРЮЛ, БКИ), скоринг, документы; действия: одобрить, одобрить на иных условиях, запросить данные, отказать, комментарий |
| Единый процесс, данные сохраняются | Всё хранится в одном хранилище; действия клиента и сотрудника меняют статус, оба кабинета обновляются сразу |
| Сохранение контекста, без повторного ввода | Профиль компании и последние финансы подставляются в новую заявку; черновик автосохраняется; «повторить заявку» после отказа |
| Пользователь без банковской экспертизы | Выбор по цели, простые формулировки, подсказки к полям, причины отказа и что делать дальше, понятное объяснение иных условий |
| Модель решения | Решение даёт ML-сервис (`POST /v1/decision`); сотрудник видит PD, скор, класс риска и факторы риска |
| Внутрипродуктовый сценарий | Нет почты, SMS и звонков: уведомления, запросы данных и ответы, подписание — внутри кабинета |
| Допустимые упрощения | Подписание (простая ЭП) и выдача средств смоделированы и помечены как имитация |
| Веб-интерфейс, без мобильного приложения | Адаптивный сайт |
| Независимость от платных ресурсов | Нет внешних сервисов и шрифтов; системные шрифты |

## Статусы заявки и маршрутизация
`submitted → scoring → {rejected | need_info | manual_review | offer} → signing → disbursed`; также `declined` (клиент отказался). Из `need_info` ответ клиента возвращает заявку в `manual_review` (или на повторную автопроверку, если запрос был системным).
- **Автоотказ:** ликвидация, просрочка >90 дн., бизнес <6 мес., PD выше 1,6× порога продукта.
- **Автоодобрение:** одобрено моделью и сумма ≤ 3 млн ₽ (`AUTO_APPROVE_LIMIT` в `js/config.js`).
- **Очередь сотрудника:** иные условия, крупные суммы, сбой проверок или недоступность скоринга.
Если ML-сервис недоступен, заявка не теряется: она уходит сотруднику с пометкой о сбое.

## Структура кода
`js/store.js` — данные, статусы, конвейер и действия (единственный слой, который нужно заменить на вызовы backend) · `js/ml.js` — клиент ML-сервиса · `js/client.js` — кабинет клиента · `js/bank.js` — кабинет сотрудника · `js/ui.js`, `js/util.js` — общие компоненты · `js/app.js` — вход, шапка, маршруты · `css/style.css` — стиль.

## Контракт для backend (замена слоя `Store`)
Сейчас данные лежат в `localStorage` браузера (демо-режим). Для подключения реального backend методы `Store.*` заменяются REST-вызовами:
| Метод Store | Предлагаемый endpoint |
|---|---|
| `login`, `register`, `logout` | `POST /auth/login`, `POST /auth/register`, `POST /auth/logout` |
| `appsOf`, `app` | `GET /applications`, `GET /applications/{id}` (клиент — свои, сотрудник — все) |
| `createApp` | `POST /applications` → backend сам вызывает ML `POST /v1/decision` и маршрутизирует (правила выше) |
| `saveDraft`, `draft` | `PUT/GET /drafts/me` |
| `makeDoc`, `addDocs` | `POST /applications/{id}/documents` (multipart) |
| `clientRespond` | `POST /applications/{id}/info-response` |
| `clientAccept`, `clientSign`, `clientDecline` | `POST /applications/{id}/{accept,sign,decline}` |
| `bankApprove`, `bankReject`, `bankRequestInfo`, `addComment`, `takeInWork` | `POST /applications/{id}/{approve,reject,request-info,comments,assign}` |
| `notifs`, `markRead` | `GET /notifications`, `POST /notifications/read` |
| `stats` | `GET /analytics/summary` |
Смена статуса на сервере можно доставлять в интерфейс опросом (`GET /applications/{id}` раз в несколько секунд) или SSE; функция `Store.subscribe` уже перерисовывает экраны при изменениях.
Объект заявки: `id, status, product, amount, term, companyName, inn, fin{revenue,netProfit,debt,avgBalance,pattern,employees}, docs[], ml{decision|error}, offer{amount,term,rate,payment,source}, rejectReason[], infoRequest{text,docs[],by,at,response}, assignee, comments[], events[]`.

## Ограничения демо-версии
Пароли и данные хранятся в браузере без шифрования; файлы свыше 400 КБ сохраняются только как запись о вложении; подписание, выдача, реестры и бюро — имитация; один браузер — одно хранилище (клиент и сотрудник видят общие данные в рамках одного профиля браузера).
